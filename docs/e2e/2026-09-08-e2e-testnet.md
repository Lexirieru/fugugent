### Why these numbers are not just print statements

1. **The target price is not invented.** The script inverts the health factor formula
   against the values it has just read itself —
   `hargaSasaran = harga × HF_sasaran × 10000 × hutang / (agunan × ltBps × 1e18)` —
   then predicts the resulting HF locally using the same `computeHealthFactor` as
   production, and **aborts before any gas is burned** if the prediction lands outside
   the zone.
2. **The $559.02 amount was not chosen by the script.** It is the output of
   `repayToReachTarget(pos, warn)` in `decide.ts` — the exact amount needed to bring HF
   back to the `warn` threshold of 1.50. The on-chain result landed exactly on
   `1500000000000000000`.
3. **The amount paid is proven, not reported.** The on-chain debt difference
   (`posSebelum.debtBase − posSesudah.debtBase`) is asserted equal to
   `hasil.amountSentUsd8`, with a tolerance of 2 units in 8-decimal base ($0.00000002) for
   two independent floor-roundings (USD8 → token units in `sendRepay`, token
   units → USD8 in `MockLendingPool._valueUsd8`). The result was **0 units**. The
   conversion is also checked in both directions before a single cent is sent. Without
   these two checks, a unit conversion off by one order of magnitude would have the agent
   pay a tenth of what it printed while HF still rose and every other assertion still passed.
4. **Every reading is anchored to a block height.** The "before" and "after" values are
   re-read with `eth_call` pinned to the block of the `setAnswer` and `repay` transactions
   (the "Jangkar blok …" lines in the output), then matched against what the adapter
   reported. An `eth_call` with an explicit `blockNumber` cannot answer from the past: a
   node that does not yet have that block throws, rather than quietly returning stale state.
   The block ordering (`repay` > `setAnswer`) and the immutability of the collateral are
   also asserted.

Spend limits active during this cycle: max $1,000.00 per action, $2,000.00 per day,
60-second cooldown. `cappedPerAction` and `cappedPerDay` were both `false` — the requested
amount really was below the limits, so what is tested here is the execution chain, not the
capping (capping, cooldown, and the kill switch have their own unit tests).

## Honest notes

1. **The repay signer in this section is the deployer EOA, not an Altana session key.**
   That is true for the run documented above and is left as is, as history. The execution
   path has since been moved to a bounded session key — the evidence, tx hashes, and the
   denial proof are in the section "Evidence of a repay through a bounded Altana session key"
   below.
2. **The lending protocol is a mock.** `MockLendingPool` was deliberately made ABI-compatible
   with Aave v3's `getUserAccountData` so that `readAavePosition` could be used unchanged;
   that is what was proven. It is not Aave, and it is not part of the product. We also pushed
   the collateral price down ourselves, on a feed we own.
3. **The sample position shrinks every time this script proves itself.** The repay is real, so
   the debt really does go down: $3,125.00 (at deploy) → $2,395.83 → **$1,836.80**
   now. HF at a $750 price therefore rises with it (now 3.06), and the "starting HF" figure
   will differ on each run. The script can still be re-run: its target price is derived from
   live readings, not from a constant.
4. **Public BSC testnet RPCs can answer stale.** The first run (of an earlier version of the
   script) failed — and failed correctly — because `eth_getTransactionReceipt` was answered by
   a node that already had block 129832787 while the following `eth_call` was answered by a
   node still at 129832786. The script now re-reads until consistent (`bacaSampai`) **and**
   anchors its proving reads to the transaction's block height, so its safety no longer
   depends on the coincidence that state only moves one way.
5. **One test had to be fixed because this E2E succeeded.** `testnet.test.ts` used to require
   the sample position's HF ≈ 1.8 — the value right after deploy. Once Guardian actually paid
   down the debt, that number no longer held and the test went red *because the product
   worked*. The assertion now is: the HF reported by the pool is matched against
   `computeHealthFactor` over the same reading (a Solidity↔TypeScript differential test), plus
   `collateralBase` and `liquidationThresholdBps` are still pinned exactly, because neither is
   changed by a repay. The test count stays 114 and all of them are green.

`msg.sender`. The old sample position was owned by the deployer EOA, so the Altana wallet
could never pay it off. So a new position was created that is **owned by the Altana wallet** —
and that is in fact the correct shape for the product: the position belongs to the user's
wallet, and the agent only holds a bounded session key over that wallet.

relay answering HTTP 502, a receipt timing out, or a nonce race all throw too, and none of them
test permissions. `assertSessionDenial` (`src/strategy/chain/session.ts`) requires the error to
actually contain `UnauthorizedCall` **and** to name the contract we tried to call; any other
shape is re-thrown as a test failure. That was proven for real, not only in a unit test: with
the relay pointed at a dead endpoint (`ALTANA_RELAY_URL=http://127.0.0.1:1`) the probe script

### Two different keyHashes for the same key

This document contains two hashes, and both belong to the same session key under different
hashing schemes. Stated here so they are not read as two keys:

| Where | Value | Formula |
|---|---|---|
| Keystore registry (`getKeys`, `isValidKey`) | `0x7a467115…` | `keccak256(publicKey)`, publicKey SEC1 uncompressed, 65 bytes |
| The `UnauthorizedCall` error (Porto/Ithaca account) | `0x80c191a2…` | `keccak256(abi.encode(uint256(2), keccak256(bytes32(signer address))))` |

Both can be recomputed from the `publicKey` printed above, with no secrets at all:

```bash
PK=04170dab…dfb88a                       # without the 0x
cast keccak 0x$PK                        # → 0x7a467115…  (Keystore keyId)

ADDR=$(cast to-check-sum-address 0x$(cast keccak 0x${PK:2} | tail -c 41))
cast keccak $(cast abi-encode "f(uint256,bytes32)" 2 $(cast keccak $(cast to-uint256 $ADDR)))
                                         # → 0x80c191a2…  (account keyHash)
```

Run, and it matches exactly. Which means that `UnauthorizedCall` really was rejecting **our
session key**, not some other key. (The identity of the session does not depend on this: the
negative control in the E2E uses the same session object that had just paid.)

### What is NOT proven

1. **The receipt does not distinguish an admin key from a session key.** Both act as the same
   wallet, and the Orchestrator does not write the signer's keyHash into the logs. What closes
   that gap: the E2E script only ever loaded the **session file** (`AltanaWalletProvider` in
   `session` mode; the admin keystore is never opened on the repay path), and the same session
   was rejected for `transfer` — whereas an admin key would never be rejected.
2. **A denial leaves no on-chain trace.** `UnauthorizedCall` appears when the relay simulates
   the userOp against the account contract; there is no block a judge can open for that denial.
   What a third party can check: the error message is a custom error of the account contract
   (that string does not exist in any `node_modules`), its keyHash matches our key, and no
   balance moved. The accurate sentence: *"rejected by the Altana account validator while the
   relay simulated it"*, not *"there is a reverted transaction on-chain"*.
3. **Altana permissions do not bind argument values** — only contract + selector. This session
   is therefore technically allowed to call `mUSD.approve(<anyone>, <any amount>)`. What holds
   it back: the per-token spend cap on the session, our own code, which only ever assembles an
   `approve` for the pool (gone the moment the process is hijacked), and the Porto guarded
   executor zeroing the allowance at the end of the userOp — **third-party behaviour we
   discovered empirically in this task**, not something our contracts guarantee. Real argument
   binding needs an intermediary contract.
4. **The contents of the allowlist are not readable from the chain.** The Altana account
   hash-commits its `permissions`; what is public is only the existence and validity of the key.

### Two spend limits, and which one binds

| Layer | Limit | Enforced by |
|---|---|---|
| `LIMITS.maxPerDayUsd8` in the E2E script (`execute.ts`) | $2,000/day, $1,000/action, 60-second cooldown | our code — gone if the process is hijacked |
| Session spend cap | 100 mUSD/day, 0.02 tBNB/day | the Altana account contract — survives even if the code is hijacked |

The stricter one wins, and that is the session cap. That is the right direction, but there is a
consequence that has to be said out loud: a request above 100 mUSD/day will not be refused
cleanly by `execute.ts` (which thinks $2,000 is still available) — it will fail at the relay as
an error. For a demo of a single $6–12 repay that gap is never touched; for production the two
have to be reconciled.

## One Altana behaviour that is expensive to discover on your own

The first run failed, and the failure was informative. `approve` was sent as its own
transaction and succeeded (`status 1`), then `repay` in the next transaction reverted:
`ERC20InsufficientAllowance(spender: 0xb3e1f06a…, allowance: 0, needed: 11666666670000000000)`.

The cause is readable in that approve receipt ([`0xf9570e1e…`](https://testnet.bscscan.com/tx/0xf9570e1e34c0942dfca694a7a8c192fb68974bd95f413ee090335d772270ae7e)):
there are **two** `Approval` events, `11666666670000000000` and then **`0`**. The Porto guarded
executor that runs spend-capped keys **returns the ERC-20 allowance to zero at the end of the
same userOp**. That is correct behaviour — an allowance from a leaked key must not outlive its
transaction — and the consequence is clear:

> **`approve` and `repay` must be in ONE userOp.**

That is why `createSessionSendRepay` sends a batch rather than two sequential transactions.
