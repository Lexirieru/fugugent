# Backend Fugugent — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development.

**Goal:** API yang memberi frontend data agent empat kategori dengan cepat dan **tidak pernah kosong**, meski 8004scan sedang tumbang.

**Architecture:** Hono + Postgres (Drizzle) + Redis. Empat lapisan: BFF ke 8004scan dengan cache dan circuit breaker; indexer on-chain sebagai jaring pengaman; classifier empat kategori; API marketplace. Setiap sumber data punya fallback berjenjang.

**Tech Stack:** TypeScript, Hono, Drizzle, Postgres, Redis, viem, vitest.

**Spec:** `docs/specs/2026-09-08-fugugent-design.md` §6 · **Riset API:** `docs/research/04-8004scan-termix-pancakeswap.md`

## Global Constraints

- **Setiap panggilan 8004scan wajib menyertakan `User-Agent` browser.** Tanpa itu API membalas HTTP 500, bukan 429 — sudah diverifikasi live. Sama berlaku untuk dGrid (membalas 403).
- **API key tidak pernah menyentuh browser.** Frontend hanya bicara ke backend kita.
- **Fallback berjenjang wajib:** 8004scan → cache Postgres → baca on-chain → seed terkurasi. Marketplace tidak boleh pernah kosong saat dinilai juri.
- Retry exponential backoff 3–5×, circuit breaker per-sumber. Upstream terbukti membalas `500 DATABASE_ERROR` intermiten — 4 dari 5 percobaan gagal saat riset.
- Cache TTL: detail agent 60 dtk · leaderboard 5 mnt · trending 1 mnt · global 60 dtk.
- Semua nilai on-chain sebagai `bigint`; jangan pernah `number` untuk uang.
- Tanpa API key, tier anonim hanya 30 req/menit — arsitekturnya harus tetap benar tanpa key, dan otomatis lebih longgar begitu `SCAN8004_API_KEY` diisi.
- Perintah dari `backend/`.

### Task 1: Fondasi — config, klien HTTP tahan banting

**Files:** `package.json`, `tsconfig.json`, `vitest.config.ts`, `src/config.ts`, `src/http/client.ts`, `src/__tests__/client.test.ts`

**Produces:**
- `loadConfig()` → alamat kontrak testnet, RPC, base URL, API key opsional
- `createHttpClient({ fetchImpl, now })` → `get(url, opts)` dengan retry, timeout, circuit breaker
- `class UpstreamError extends Error` membawa `status` dan `attempts`

**Aturan mengikat:**
- Header `User-Agent` browser **selalu** dikirim. Ada test yang memastikan ini; tanpa header, request dianggap cacat.
- Retry pada status 5xx dan kegagalan jaringan; **tidak** retry pada 4xx selain 429.
- Circuit breaker: setelah N kegagalan berturut-turut, tolak cepat selama cooldown, lalu izinkan satu percobaan pengintaian.
- `fetchImpl` dan `now` disuntikkan — test tidak menyentuh jaringan.

Test wajib: User-Agent selalu ada; 500 di-retry lalu berhasil; 404 tidak di-retry; breaker membuka setelah ambang; breaker mengizinkan pengintaian setelah cooldown; timeout menghasilkan `UpstreamError`.

- [ ] Setup paket + tsconfig + vitest → [ ] test dulu → [ ] gagal → [ ] implementasi → [ ] hijau → [ ] commit

### Task 2: Sumber 8004scan + sumber on-chain

**Files:** `src/sources/scan8004.ts`, `src/sources/onchain.ts`, test masing-masing

**Produces:**
- `listAgents({ chainId, limit, offset, filters })`, `semanticSearch(q, opts)`, `getAgent(chainId, tokenId)`
- `readFuguListings()` membaca `FuguRegistry` di testnet (`0xb2f36070E6eae3353E8e755172B477DF213ae248`), `listingCount()` dan `getListing(id)`
- Normalizer yang mengubah kedua bentuk respons menjadi satu tipe `AgentRecord`

**Aturan:** bentuk respons 8004scan **tidak seragam** (`{items}` vs `{success,data}` vs `{success,error}`) — normalizer wajib menangani ketiganya dan tidak melempar pada bentuk tak dikenal, melainkan mengembalikan daftar kosong plus menandai sumber tidak sehat.

Test: normalizer untuk ketiga bentuk; filter spam (`is_registered`, `min_score`, `has_a2a`) benar-benar dikirim sebagai query; pembacaan on-chain memakai alamat dari config.

### Task 4: Classifier empat kategori

**Files:** `src/classify.ts`, test

**Produces:** `classify(agent): { category: Category | null; confidence: number; reason: string }`

**Aturan:** murni, tanpa I/O. Lapis pertama kata kunci pada nama/deskripsi/tag; lapis kedua OASF skill/domain bila ada. Kembalikan `null` bila kepercayaan di bawah ambang — lebih baik tidak mengategorikan daripada salah mengategorikan. Kategori: `REBALANCING`, `GRID`, `YIELD`, `HEALTH_FACTOR`.

Test: setiap kategori punya minimal tiga contoh positif dan satu negatif; agent tak jelas menghasilkan `null`.

---

### Task 5: Service dengan fallback berjenjang

**Files:** `src/service/agents.ts`, test

**Produces:** `getAgentsByCategory(category, opts)`, `getAgentDetail(id)`, `getHealth()`

**Aturan mengikat — inilah inti nilai juri:**
1. Coba 8004scan.
2. Bila gagal atau breaker terbuka → cache Postgres, tandai `stale`.
3. Bila cache kosong → baca on-chain (`FuguRegistry`).
4. Bila masih kosong → seed terkurasi dari file.
Hasil **selalu** menyertakan `source` dan `ageSeconds`, supaya UI dan juri tahu dari mana angkanya.

Test: keempat tingkat fallback dipicu berurutan dengan sumber yang disuntik; `source` benar di tiap tingkat; tidak pernah melempar ke pemanggil.

### Task 6: Endpoint HTTP + health

**Files:** `src/routes/agents.ts`, `src/routes/health.ts`, `src/index.ts`, test

**Endpoint:** `GET /api/agents?category=&limit=&offset=`, `GET /api/agents/:id`, `GET /api/categories` (jumlah per kategori), `GET /api/health` (status tiap sumber, jujur).

**Aturan:** `/api/health` menampilkan keadaan sebenarnya tiap sumber termasuk yang sedang tumbang — ini yang membuat klaim ketahanan kita bisa diperiksa, bukan sekadar diucapkan.
